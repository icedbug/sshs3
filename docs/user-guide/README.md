# sshs3 user documentation (source)

These Markdown files are the **single source** of the documentation published at <https://docs.sshs3.com>.
The site repo (`sshs3-site`) only holds the presentation: templates, the page registry and the build. Edit the
text here, in the same commit as the code it describes (see [CONTRIBUTING.md](../../CONTRIBUTING.md)).

## How it gets published

`scripts/deploy-site.sh` (run by `scripts/deploy.sh` when `docs/` changed, or on its own) rebuilds the site from
this checkout: `npm run build:docs` in `sshs3-site` reads these files, the IPC channels and keyboard shortcuts
(extracted from `src/shared/types/ipc.ts` and `settings.ts`) and renders them through the site templates.

- **One file = one page.** The page list, order, titles and summaries live in `sshs3-site/scripts/build-docs.js`
  (the `modules` registry). A new page needs a file here **and** an entry there. This README is not a page.
- **Screenshots** live in [`docs/screenshots/`](../screenshots) and are referenced as `/img/docs/<name>.png`
  (they are synced to the site on deploy; the references do not render when browsing the files on GitHub).
- **Generated blocks:** `{{AUTOGENERATED_SHORTCUTS_TABLE}}` and `{{AUTOGENERATED_IPC_TABLE}}` are replaced at build time.
- **Page title:** the build renders the registry title as the page's `<h1>` and drops the file's own leading `## Title` line (it stays for readers on GitHub), so start each file with that line and use `##` for the numbered sections.
- **Build guards:** the build fails if a page in this folder is missing from the registry, or if a registered file is missing. Legacy URLs (`/docs/<old-slug>/`) are redirected by the site Worker (`src/index.ts`), so renaming a page's slug needs an entry there.
- **Site syntax:** `<!-- tabs:… -->` / `<!-- tab:Title -->` for tabbed code, `> [!NOTE]` / `> [!IMPORTANT]` for callouts,
  and fenced `mermaid` blocks for diagrams. Inline code is escaped, so `<placeholder>` and `*.log` are safe in backticks; outside backticks a bare `<tag>` disappears. Do not put a `> [!NOTE]` callout inside a list item (it is not parsed there); end the list or write it as bold text. They degrade to plain Markdown elsewhere.
- **Language:** English only.

## Page style (v2)

Every page follows the same shape, so new and updated text should too:

1. **Title line** `## <Title>`, one intro paragraph, then the page's hero screenshot. Follow with numbered sections `## 1. …`, `## 2. …`; a short `### …` subsection per feature. No emoji in headings and no Purpose / How to Use / Limitations blocks per feature.
2. **Tables for reference data:** shortcuts, settings (label, default, effect), options and metrics go in tables, not bullet walls. Use `<kbd>` per key and the exact UI label in **bold**.
3. **Callouts for caveats:** put limitations and gotchas next to the thing they affect as `> [!NOTE]`, `> [!TIP]`, `> [!IMPORTANT]` (a titled "Good to know" list is fine) or `> [!WARNING]`. Do not drop a caveat to save space; shorten it instead.
4. **Internals stay short:** one `### Technical Architecture: …` (or `Technical Internals`) subsection per section, naming the module and the user-visible consequence. No `<details>` folding.
5. **Troubleshooting last:** a `## N. Troubleshooting & Diagnostics` table (Symptom / Probable Root Cause / Corrective Action) closes the page.
6. **Cross-links** use the new URLs (`/docs/workspace/terminal/`, `/docs/security/team-vault/`, …), never the old flat slugs.

`npm run docs:lint` (`scripts/docs-lint.mjs`) checks this style: the title line, no emoji headings or retired blocks, no `<details>`, no callout inside a list, no bare `<tag>` outside backticks, balanced tables and fences, old flat or unknown page links, missing screenshots, shortcuts that are not defaults in `settings.ts`, plus numbered sections and a closing Troubleshooting section as warnings. It runs in pre-commit, in the docs CI workflow (`--strict`) and before `deploy-site.sh` builds. A page that legitimately has no Troubleshooting section goes on the allowlist at the top of the script.

Before committing, run the site build (`npm run build:docs` then `npm run validate:links` in `sshs3-site`) and check the page in a browser in both themes.

## Writing rules

- Describe what the app does today; verify button and setting names against the UI (`src/renderer`) and
  `src/shared/types/settings.ts`. Do not document settings or labels that do not exist.
- Use the exact UI labels in **bold** and keyboard shortcuts in `<kbd>`.
