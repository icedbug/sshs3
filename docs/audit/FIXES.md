## Notes

- SEC-03-001 follow-up (`aefa027`): the saved passphrase only answers ssh's own `Enter passphrase for …` prompt. A later automated review asked for a stronger guarantee (ssh version check, or answering at most once). Not done: it rests on OpenSSH prefixing server keyboard-interactive prompts with `(user@host) `, which has not been tested against a real `ssh`.
- SEC-11-001: a `session.json` written by an earlier version may still hold secrets until the next save rewrites it (the app saves on startup once the session has loaded; `SessionStore` also sanitizes on read).
- Verified, not fixed (needs a decision): BUG-06-001 / BUG-11-001. `disconnectStorage` has no caller in the renderer, so SFTP children, askpass servers and per-session agents live until the app quits or the profile is saved; and `StorageRegistry.getOrCreate` returns an existing provider and ignores the new config, so a password typed after a failed first attempt is ignored unless it is saved to the profile (saving disconnects). ## Session restore after SEC-11-001 (found by running the app)

SEC-11-001 stopped file manager tabs from writing their secrets to `session.json`, which is right, but a tab restored after a restart then had no password, passphrase or secret key. Run in the real app with a saved SFTP profile (password) and a saved S3 profile:

- **S3 tab after a restart:** it connected with no secret key (`secretAccessKey` is taken straight from the tab's config). Not shown against a real S3 server; the inference rests on the session file and `S3StorageProvider.ts`, so a real server would be expected to reject it.

**Fix:** `lib/savedSecrets.ts` (`withSavedSshSecrets`, `withSavedS3Secrets`) fills in what a restored tab lacks from the saved profile, matched by profile id, only the fields that are missing (password, passphrase, S3 secret key, session token, proxy password; never a PIN), and not from a deleted profile or one whose authentication type has changed. `DualPaneExplorer` applies it where a restored tab connects by itself. Secrets stay out of the session file. 6 unit tests (`tests/renderer/savedSecrets.test.ts`); re-run in the app: after a restart the SFTP tab shows no dialog and connects straight away, as before the restart. ### Follow-up: the restored secrets must not follow an edited target (automated security review of `d3ee1f3`)

The first version of `savedSecrets.ts` matched a restored tab to its profile by id alone. The session file is not protected against being edited, and since the fix to SEC-11-001 it no longer holds the secrets itself, so editing a tab's `host` to another server and restarting would have made the app fill in the profile's password and connect there. The secrets are now only filled in when the tab still names the same target as the profile: for SSH the host, the port (a missing port is 22) and the user; for S3 the endpoint, the region and the access key; for a proxy password the proxy's host and port (the rest of the profile's secrets still follow when only the proxy differs). A tab opened by the app itself always matches, so normal restores are unaffected. Tests for each mismatch (they fail without the change). Not done: rebuilding the whole connection from the saved profile and taking only view state (paths) from the session, which would be stricter but is a larger change.

### Decision on `apply()` trusting its entries: left as it is

Correction to the note above: an absolute `relativePath` does **not** escape the target (`joinPaths` strips leading slashes for remote targets and `path.join` puts it under the target for local ones); only `..` segments do. And `relativePath` is not the only thing `apply()` trusts from the renderer: a delete uses the entry's own `targetEntry.path`, and a copy reads from `sourceEntry.path`. A real guard would rebuild every path from `relativePath` and check that it stays under the root (or check the entry paths against it), for both copying and deleting, with tests for both. Decided not to do it: the entries come from the renderer, which can already call the storage IPC with any path, so `apply()` gives it no new capability; the guard would only protect against a bug in the renderer. Paths the app builds itself cannot leave the tree (`buildTree`, tested).
